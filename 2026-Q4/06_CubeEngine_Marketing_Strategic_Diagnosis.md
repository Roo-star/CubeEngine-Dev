# CubeEngine / CubeUniverse：项目级 Marketing 战略诊断

日期：2026-09-17｜状态：Promotion重建的研究底座，不是渠道排期或最终营销方案。

## 1. 结论先行

CubeEngine不是普通AI游戏引擎、3D游戏集合或单一游戏产品。它提出的是一种新的设计与生产操作：**把已有的离散网格游戏作为来源事实，在保留核心规则身份的基础上进行空间维度扩展，并把得到的系统继续变成可编辑、可执行、可验证、可训练的3D游戏。**

CubeUniverse则不是装这些产品的盒子。它是把“维度扩展”这一思想、CubeEngine的技术能力、由此产生的可玩实验与Providence原创作品连接起来的统一IP。三者的关系应当是：

```text
维度扩展的思想（为什么值得重新想象）
        ↓
CubeEngine（如何系统地把它实现）
        ↓
Demo / Providence / 后续作品（这种能力能创造什么）
        ↓
新的体验、创作与合作继续反哺CubeUniverse
```

因此，当前Marketing真正要建立的不是某种产品形态，而是三种外部认知：

1. **这是一个值得记住的新概念**，不是普通3D视觉包装。
2. **CubeEngine确实在建立可重复的能力**，不是为每个Demo手工重写。
3. **这种能力能够持续产生有意义的体验与作品**，而不是只有一次新奇。

在这三层没有成立前，直接决定“玩家还是创作者”“两个游戏还是五个”“LinkedIn还是Discord”，都属于过早落地。

## 2. 项目的真实技术与体验逻辑

### 2.1 用户看到的一步，背后不是一步

理想体验看起来可以是：载入2D游戏、表达设计意图、得到3D空间版本。但当前技术路线要求后端严格区分：

```text
来源项目
→ 来源证据与可运行基线
→ Rule / Scene / Asset / Input IR
→ 设计师确认来源事实
→ Spatial Lift Plan
→ 目标3D IR
→ 确定性验证、编译和执行
→ 可编辑场景、可玩体验和适用时的AI接口
```

LLM负责处理开放式理解和提出结构化方案；确定性核心负责拒绝不可靠结果、保证状态、时间、随机、输入、重播和执行边界。它不是让LLM为每个游戏自由生成一套孤立代码。

### 2.2 空间升维不是“加一层Z轴”

真正的升维会改变：邻域、移动、生成、碰撞、路径、胜负条件、资产表达、镜头与输入。不同游戏需要明确的空间策略。例如，3D扫雷的邻域可能从平面的8邻格变成体积中的26邻格；Connect、Snake和2048又分别涉及连线、连续移动和有序合并。

这正是项目的技术与设计价值：它试图把这些变化从一次性手工设计，提升为一种可描述、可审查和可重用的系统。

### 2.3 当前PoC能证明什么，不能证明什么

当前公开评审包提供Source 2D、Transformed 3D和Project Session三种互补展示；已有Snake、Minesweeper、Connect Four和2048等经过测试的空间适配案例，以及内置的确定性IR／AlphaZero接口验证路径。

它可以支持的当前证据包括：

- 原2D与3D结果可并列体验；
- 多类规则在加入Z轴后产生不同的空间变化；
- 引擎核心可以通过统一的状态、输入、运行和重播路径工作；
- PoC不是只有井字棋视觉效果。

它目前不能诚实证明：

- 任意未见游戏都能自动完成端到端转换；
- LLM编译器已经普遍可靠；
- 全部3D场景都已在统一编辑器内完整编辑；
- AI模型已经对所有兼容游戏自动训练并达到产品级质量；
- 转换效率、用户需求、价格与商业模型已经验证。

Marketing必须保护这个证据边界。愿景可以大，但当前陈述必须区分“已经可演示”“正在建设”“未来可能”。

## 3. 项目的独特性到底在哪里

### 3.1 不是单纯的AI能力，而是专用转换语法与可信执行边界

Unity、GDevelop等产品也在把理解项目上下文的AI放进编辑器。GDevelop官方明确强调其Agent读取场景、对象和变量并直接修改项目；Unity同样强调in-project context和控制能力。因此，“AI理解游戏项目”“自然语言改游戏”本身正在成为相邻工具的常见主张。

CubeEngine更独特的方向是：它不是泛化地帮助制作任何功能，而是围绕**已有游戏的来源身份、空间规则转换和3D目标版本**建立专用合同；AI可以提出解释，不能越过确定性验证。传播不能停在“AI-powered game engine”，否则会掉进一个拥挤而模糊的比较框架。

### 3.2 它把“转换过程”本身变成创作媒介

通常一个游戏引擎帮助人从空白或模板开始制作游戏。CubeEngine的特殊入口是：一个已经存在的规则世界，经过设计师可参与的空间升维，成为另一个仍可辨认、但策略结构发生变化的世界。

这意味着它兼具：

- 工具价值：减少重复搭建空间逻辑、验证、表现和AI接口的成本；
- 设计价值：提供一套探索平面规则如何在空间中变化的方法；
- 内容价值：每次转换都能产生可体验、可讨论的作品；
- IP价值：这些作品共享“Cube化／维度扩展”的文化记忆。

四种价值来自同一机制，不应该在品牌上切割。

### 3.3 内容不是引擎的附属广告，而是引擎的真实性证明

技术工具的能力往往不能靠功能列表让外界真正理解。Unreal Engine 5首次展示用实时运行场景让观众先看到核心技术产生的结果；Blender长期使用Open Movies在真实制作中测试工具、推动开发并让作品证明生产能力；Dreams则以Art's Dream作为其创作工具潜力的官方示范，同时把Play、Create、Share保持在同一宇宙内。

这对CubeUniverse的启示不是模仿它们的规模，而是：**作品、Demo、引擎与品牌可以互为证据。** Providence和多个空间转换案例并不会天然分散品牌；只有在缺少共同主张与清晰关系时才会分散。

## 4. 真正的Marketing难题

### 4.1 最大问题是“证明断层”，不是没有渠道

外部看到一个3D扫雷或3D井字棋时，无法自动知道：

- 它是否由同一引擎路径产生；
- 规则是否来自原游戏而非团队重新设计；
- 升维是可控制的方法还是预制效果；
- 换一个游戏是否仍然有效；
- 这个变化是否真的增加玩法价值。

因此一段漂亮视频最多证明“有一个有趣结果”，不能单独证明“有一个可重复的引擎”。Marketing必须设计证据组合，而不是只做内容数量。

### 4.2 Cube非常直观，也非常容易被低估

立方体有强烈视觉符号，品牌易被记住；但同一优势也可能把项目压扁成“把棋盘立体化”的视觉梗。每次关键展示都需要让人看到至少一个规则后果，例如邻域、路径、合法动作、胜负或信息可见性怎样改变。否则视觉越强，技术误解可能越深。

### 4.3 认知负担是产品问题，也是传播问题

3D空间会带来遮挡、坐标理解、视角和输入困难。对于这个项目，“看不懂”不能简单解释为受众不对；也可能是视角、切层、高亮、教学或展示顺序没有完成工作。

传播材料需要把复杂性变成戏剧性的理解过程：先给熟悉基线，再只引入一个空间变化，让观众看到自己的旧直觉如何失效，最后显示系统怎样帮助他重新理解。

### 4.4 “AI”如果不分角色，会制造错误期待

项目至少涉及四种不同语境：

- LLM对来源游戏和设计意图的理解／编译；
- 非LLM核心的验证与执行；
- MCTS／RL等游戏AI及训练接口；
- Providence中的AI事件／内容桥接。

如果全部压成“AI Engine”，技术受众会怀疑准确性，普通受众会期待一句话生成完整游戏，合作方也难判断可交付物。品牌可以统一，能力名称必须精确。

### 4.5 公开与保护之间不是“全藏”或“全说”

完全不展示会无法证明引擎；公开架构、算法与实现细节又增加复制和专利风险。更合理的披露层次是：

- 公开结果：2D／3D对照、真实操作、规则变化、多个案例、当前限制；
- 公开方法轮廓：来源理解→设计选择→验证→可玩结果；
- 受控展示：完整工作流、具体参数和可交互Build；
- 保留内容：IR细节、转换逻辑、代码、内部架构、未申请保护的技术实现。

能证明“这是一套系统”不等于必须公开“系统是怎样实现的”。

## 5. 优势、弱点与战略含义

| 真实情况 | Marketing含义 |
|---|---|
| 2D→3D前后变化视觉强、能在数秒内制造疑问 | 适合形成记忆钩子，但后续必须解释规则变化 |
| 多个不同机制已有可玩示例 | 可建立“不是一次性Demo”的证据；不可宣称任意游戏自动转换 |
| 引擎、玩法设计、AI与原创作品互相连接 | 具备形成长期IP叙事的条件，不应拆成互不相关的账户和品牌 |
| Founder本身同时具有游戏设计、空间体验和产品方向 | Founder叙事可以成为早期可信入口，尤其适合解释设计思想与过程 |
| 技术价值需要运行过程才能理解 | 静态海报和宽泛口号不够，真实操作与前后对照是核心媒介 |
| 当前通用LLM转换、编辑器体验和AI产品化仍不完整 | 不能把愿景当现状；应把“正在解决的难题”转化为可信研发叙事 |
| 3D规则可能更有趣，也可能更混乱 | 必须同时展示惊奇和可理解性，不能只追求视觉震撼 |
| 多种未来商业形态都有可能 | Promotion应建立概念、证据与关系资产，不替Founder提前锁定产品形态 |
| 核心概念可被模仿 | 防御不只靠保密：还包括申请节奏、可辨识语言、作品连续性、研发速度、可信证据和关系网络 |

## 6. 谁应该先出现：不是“玩家／创作者”二选一

第一阶段不应该按人口标签或未来商业模式划分，而应按对当前最大不确定性的贡献选择人。

### 6.1 第一圈：能够判别主张真假的“高信息观察者”

包括真正做过规则系统、游戏工具、关卡／系统设计、技术美术、交互原型或相关AI流程的人。他们的作用不是被预设为客户，而是回答：外部专业人士能否分清空间升维、手工重做与通用AI生成？哪一段证据最可信？哪里仍像视觉噱头？

筛选依据是近期做过什么和能判断什么，不是“创作者”这个泛标签。

### 6.2 第二圈：能够亲身感受到规则变化的人

包括熟悉某个来源游戏、空间谜题、棋类变体或复杂交互的人。他们的作用是判断：改变是否可以理解，是否产生新的决策，而不仅是画面更复杂。

这仍不等于把项目定义成面向玩家。它验证的是CubeUniverse必须兑现的体验层。

### 6.3 第三圈：能够把复杂概念解释给别人的“转译者”

包括擅长讲解游戏机制、工具、互动技术或设计过程的内容作者、活动主持人、教师和策展人。他们只有在前两层证据清楚后才有价值，否则只是帮助扩散混乱信息。

### 6.4 第四圈：可能配置资源的关系方

包括工作室、IP持有方、孵化机构、技术伙伴、研究／教育合作方。应根据其具体兴趣展示相同IP的不同证据，但不为每类人重新发明一个项目身份。

一个人可以同时属于几圈。这里没有8:4或任何固定比例。第一轮先定义需要回答的判断题，再选择最少但信息密度足够的人；当新增接触不再产生新的关键问题时，再转入下一圈。样本数量随后根据实际招募和证据稳定程度制定，而不是先拍一个整数。

## 7. Promotion之前必须建立的“证据阶梯”

| 层级 | 外界需要相信什么 | 最合适的证明 |
|---|---|---|
| 1. 概念可见 | 维度扩展不是普通3D皮肤 | 一个熟悉规则的2D／3D前后对照，明确指出一个规则后果 |
| 2. 结果可玩 | 这不是概念图或预渲染 | 真人实时操作、失败和修正都可见 |
| 3. 来源可追 | 目标版本仍与来源身份有关 | 同一来源的状态、输入、结果或素材角色对照；无需公开底层实现 |
| 4. 方法可重复 | 不只是一个手工特例 | 两到三个机制差异明显的案例使用相同展示结构 |
| 5. 设计师可控制 | 引擎不是黑箱随机生成 | 展示一个可公开的空间参数或设计选择怎样改变结果 |
| 6. 能力可扩展 | 这可能支持更大的世界和作品 | 当前路线、下一能力及Providence等原创内容的真实进展 |
| 7. 品牌可归属 | 这些发现都来自同一IP | 一致命名、视觉、解释语句与CubeUniverse入口 |

Marketing内容、渠道和活动必须服务其中某一层。不能指出自己在证明哪一层的动作，应从计划中删除或降级。

## 8. 现有Pitch的Critical Review

### 8.1 最有价值的部分

- “Spatial Dimension Expansion Engine”比“AI Game Engine”更具辨识度。
- 2D→3D视觉对照与Cube符号具有强记忆性。
- Engine、原创游戏和后续生态有成为统一品牌叙事的基础。
- Founder的游戏设计和空间项目经历，与项目的跨技术／创作特性高度一致。

### 8.2 当前最需要修正的部分

- “2D策略深度被AI耗尽”是一个宏大且容易争辩的前提，并不是理解CubeEngine价值的必要条件。它会把讨论带向棋力和市场衰退，而不是维度扩展的创造价值。
- “any game”“one-line configuration”“few hours”“world's first complete stack”等语句超过当前证据边界；愿景可保留，但必须改成目标、适用范围和当前进展。
- Engine、Consumer Platform、SDK、Providence、教育、IP授权和AI训练在同一层出现，容易让外界不知道现在究竟完成了什么。统一IP不等于一次把所有未来业务说完。
- 旧商业模型中的固定受众、Steam／Reddit／Discord渠道和平台路线属于假设，不是已经研究出的策略。
- “专利＋先发＋训练数据＋网络效应”目前是计划中的防御机制，不是已经形成的护城河。

## 9. 已完成的research与仍缺的research

### 9.1 本轮已经核对

- 项目PRD、最新引擎架构、非LLM核心原则、集成审计、可分发PoC说明；
- CubeUniverse现有Pitch的14页内容与视觉结构；
- 指定开发对话中的来源事实、Design Intent、IR、Approval和公开边界讨论；
- Unreal Engine的技术Demo式亮相；
- Blender用Open Projects在实际制作中验证工具并用作品建立认知；
- Dreams用旗舰作品、创作工具和社区作品共同解释一个创作宇宙；
- Unity／GDevelop的项目上下文AI，确认“AI理解项目”不是足够独特的定位；
- MIT Lead User研究，支持早期寻找真正经历前沿需求、能进行高信息判断的人，而不是泛用人口标签；
- 新品类研究关于核心身份框架的重要性，支持CubeUniverse需要统一、稳定的类别叙事。

### 9.2 在决定最终Promotion策略前仍要完成

1. **PoC证据审计：**把09月底真实Build能演示的每一步列成“已完成／实验性／不可公开／尚未完成”。
2. **相邻方案实测：**不是只列竞品名称，而是亲自比较通用引擎、AI Agent、单一3D变体和创作平台在同一任务上的输入、控制、验证与输出。
3. **认知测试：**用同一真实PoC制作不同证据顺序，观察外部人首先把它理解成视觉Demo、游戏、AI工具还是空间转换引擎，以及哪种演示能纠正误解。
4. **高信息访谈：**围绕实际工作和判断能力选择对象，先理解他们如何处理相近转换／规则／原型问题，不询问泛泛的“你会不会使用”。
5. **披露与权利审计：**在决定公开内容前，确认专利申请状态、第三方游戏与资产许可、Build分发和录制边界。
6. **Founder品牌意图：**明确本季度希望CubeUniverse在人们脑中首先占据的一个短语、一个情绪和一个动作。具体创意由Founder决定，Marketing负责使它可理解、可兑现和可持续。

完成这些，才有依据决定渠道、首轮对象、内容顺序、公开范围和指标。

## 11. 下一版Promotion策略必须从哪里推出

下一版不能从平台清单开始。正确顺序是：

```text
项目核心主张
→ 外界最容易产生的误解
→ 需要建立的证据阶梯
→ 每类证据由谁最有能力判断／转译／配置资源
→ 哪种内容可以证明
→ 哪个渠道能把这种内容送到这个具体的人
→ 当前团队是否有能力承接
→ 才决定数字、频率和日期
```

因此，真正的Promotion战略母题应是：**让“维度扩展”成为一个可看见、可操作、可相信、可持续产生作品，并明确属于CubeUniverse的概念。**

具体口号、视觉创意和最终产品形态不在本诊断中替Founder决定。
