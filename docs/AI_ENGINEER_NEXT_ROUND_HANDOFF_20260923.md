# CubeEngine：AI 工程師下一輪工作說明

**版本基準：最新遠端 `SRTP`，本輪更新已推送。** 請先將 SRTP 合併同步到工程師的 `llm` 分支，再開始開發；交付後合併回 SRTP。

## 目標：讓三款完整遊戲真正跑通轉換

本輪完成 **井字棋、掃雷、2048** 的真實工作流：

**完整 2D 源碼 → Compile → Approve Source → 簡短自然語言 Spatial Lift → Approve Target → Transformed 3D 可玩。**

品質對齊現有手寫成功案例：不僅有三維棋盤，還要玩法正確、輸入有效、狀態可見、勝負與重開完整。原素材、配色、字體及必要反饋應默認保留，不要求使用者在 Prompt 裡逐項補規格。

## 目前改了什麼，為什麼還沒完成

現在已是 **Rule → Asset → Scene → Input 分階段生成、執行驗證與局部修復**；已接通共用 OpenRouter 客戶端、源碼跨檔讀取、付費結果缓存，以及由四 IR 驅動的 Ursina 後端。

後端已補整體立方體布局、格壳與內容分離、原素材呈現、實際拾取／輸入、重開、session 隨機種子及回放；最新也修了井字棋棋子縮小不可見、錯誤高亮、掃雷讀取／解析邊界和測試棋盤被忽略等問題。

**但模型仍可能誤用函數、漏掉核心玩法；編譯通過也不等於遊戲品質通過。下一輪重點是源碼理解、正確生成、自動修復與獨立驗收，不是換模型或繼續手改產物。**

## 下一輪：具體改 LLM 編譯器的哪些部分

工程師要修改的是**模型收到什麼、按什麼指令生成、各次呼叫怎樣銜接、生成錯了怎樣讓模型修正**。下面前三項是 LLM 生成流程的開發，第四項驗證這些修改是否有效。

1. **改 Source 編譯的 Prompt 與上下文組裝。** 修改 `source_workspace.py`、`staged.py`：讓模型讀到完整主循環、規則依賴、輸入與素材；在生成前梳理必須保留的機制，並將這份理解帶入後續階段。重點解決掃雷讀完源码仍漏掉首步保護、揭格、展開和勝負。交付可重用的理解／生成指令與上下文管理程式，不只交人工功能清單。

2. **改 Spatial Lift 的轉換 Prompt 與生成方案。** 將手寫成功案例的方法提煉成模型可使用的通用指令和範例：如何把二维规则升維、保留外觀、生成 Scene／Asset／Input。把引擎的真實函數用法一同提供，例如合併函數的倍率參數。讓一句簡短意圖能驅動完整方案及四 IR 生成，避免模型靠猜 API、漏功能或只增加 Z 數值。交付 Prompt／範例、階段間資料傳遞及必要的構建器修改。

3. **改模型的自動修復流程。** 修改 `staged.py` 等調用程式：把執行失敗轉成模型可修正的反例，例如「輸入2、2，預期4，實際8」，附原定義和函數說明，再讓模型修正失敗階段並重驗。保留成功階段；修復受總費用／次數限制，同錯停止。交付能處理這些現場錯誤的通用修復流程，不人工改生成的 Manifest。

4. **用真實模型驗證生成能力。** 用改好的 Prompt 和流程，從原始源码重新轉換井字棋、掃雷、2048；由工程師在 Workbench 實際遊玩並記錄成功率、修復次數、費用與畫面。發現問題回到前三項修改，以原遊戲基準驗證規則，不能只採信模型自己的測試。交付三款新生成的完整結果及測試記錄。

優先改生成與修復流程，沿用現有後端。只有確定模型所需能力尚未被後端支持時，才同步補該通用能力、模型說明及測試；完整菜單、悔棋、AI 等未完成項仍須如實列明。

## 交付與驗收

- **程式＋回歸：** 提交可合併的修改，先通過 `python -m tests.run_offline_acceptance`。離線通過只是工程基線，不代表真實模型轉換通過。
- **三款真實新生成結果：** 各交完整 Source／Target 包、簡短 Intent、原始回應與修復記錄，以及 Workbench 全流程遊玩錄影。最終驗收不復用舊生成缓存、不人工改 Manifest、不用手寫示範替代。
- **品質與成本表：** 分別報告 Source 保真、Target 規則、實際可玩、外觀差距，以及請求數、token、費用。付費聯調先定預算，調試可復用已付費結果；不要讓使用者靠反覆 Compile 找問題。

**完成標準：三款均通過真實生成與遊玩驗收；單一井字棋包成功、JSON 合法或窗口能打開，均不算完成。**
