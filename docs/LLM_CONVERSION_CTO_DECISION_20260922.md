# CubeEngine 自动二维→三维转换：技术审查与开发决策

日期：2026-09-22。审查对象：`E:/CubeEngine/CubeEngine-SRTP` 的 `SRTP` 当前工作区，HEAD `a0d817832ea24659ae3116d23b0b50b325753522`，包含此前未提交改动。本文不是对某个干净提交或工程师个人工作的归责报告。

本轮完成源码、历史需求与研究资料审查，以及离线能力探针；没有新增模型调用，没有生成新的示范游戏，没有改动产品代码。原始结果见 [审查证据](E:/CubeEngine/CubeEngine-SRTP/docs/LLM_CTO_AUDIT_EVIDENCE_20260922.json)。

## 1. 产品目标与决策

**CubeEngine 必须在 Workbench 内，接收原始完整二维游戏项目，通过接入的 LLM 自动构建、验证并运行可玩的三维版本。规则、交互、外观、游戏流程共同构成转换结果。质量以已有手写 Transformed 3D 游戏，以及用户指定的 Ursina 井字棋为基准。**

默认保留原游戏的视觉身份与完整玩法，自动补齐三维操作。自然语言用于改变空间尺寸、玩法或其他特殊要求；用户不应重复输入“请保留配色、贴图、字体、胜负、重开、让它能玩”等基本要求。

决定：**保留四 IR 与统一运行时作为后端契约；重构编译前端和验证流程；补齐通用 Ursina 场景/资源后端。** 当前“压缩证据→一次生成四份底层补丁→校验→批准”的流程不足以承担这个目标。不继续以字段兜底、人工填写 Manifest、优先启动某个 Target、更多示范截图作为主线。

这是针对当前网格游戏的工程路线，不是“任意 Python 游戏都能无损自动变三维”的已验证承诺。首轮覆盖井字棋、Connect Four、扫雷、2048、Snake；通过更改源码的独立样例检验泛化。

本文替代旧产品方向文档中“先附加参考包验证入口”的用户验收顺序。旧的“一周接入＋后端保持不变＋先做 LoRA”工单不能继续作为此次完整游戏转换的范围与工期依据。历史文档保留作为记录，不叠加执行互相冲突的要求。

## 2. 当前问题不是一个 Gemini 错误，也不只是规则问题

### 2.1 实际输入已经丢失重要源码

检查生产路径 `SourceGameImporter.import_path → build_evidence_pack`，保持默认预算，结果如下：

| 完整源游戏 | 证据包 JSON 字符数 | evidence 中保留的源码片段数 |
|---|---:|---:|
| 井字棋 | 16,191 | 0 |
| Snake | 20,212 | 0 |
| 扫雷 | 20,565 | 0 |
| 2048 | 20,923 | 0 |
| Connect Four | 16,486 | 0 |

`evidence.py:671` 超过预算后首先删除所有 `snippet`，继续裁剪后仍可能超出默认 14,000 字符。剩余内容包含静态摘要、部分规则和出处信息，不能说模型毫无信息；但文件路径和行号不能代替完整函数体、调用关系和运行行为。当前调用链也没有让模型按需重新读取缺失函数的工具循环。

证据主题还将随机逻辑归为 `food_spawn`、终局归为 `death`，体现了 Snake 导向的抽取假设。把同样提示用于扫雷与井字棋不代表真正理解了这些游戏。

### 2.2 有些“修复”会破坏语义

离线探针证实：`compiler.py:4669` 的 `_coerce_expression` 对未知表达式，在 `fallback=True` 时返回字面值 `true`。动作合法性使用这一兜底，就可能把“格子必须为空”等未能编译的条件变成“允许执行”。这与 `coordinate→coord` 一类明确类型别名修正完全不同。

开发要求：机械字段、合法别名和哈希可以确定性补齐；合法性、胜负、状态更新、隐藏信息不可猜测或静默删除。无法识别的语义必须进入定位、修复或明确不支持状态。测试必须验证错误不会被改成合法成功。

### 2.3 输出结构压力代替了游戏理解

`prompts.py:23` 明确要求省略 `claims/tests/extension_proposals/spatial_lift_options`，同时让模型一次返回四 IR 的补丁。当前主要反馈来自 JSON、schema、引用等校验；这些必要，但不足以发现“落子永远写玩家 1”“蛇每次写固定格”“合并顺序错误”等行为问题。

这不是要求再加一长段提示，而是要求拆分编译任务，保留源码访问能力，让编译器能运行、观察失败并局部修复。

### 2.4 视觉声明尚未成为完整画面

`asset_ir_v2/compiler.py:402` 的 extrusion、cube_face_projection 等产出的是呈现配方描述；配方合法不代表已经创建正确的 Ursina 几何、材质和交互。Scene 编译器产出的场景命令也需要真实后端消费。

此前新增 `project_viewer.py` 按网格状态画通用立方体和数字，并不是完整 Scene/Asset 实现。这解释了为什么能够生成有效 Target，却没有达到已有三维游戏的外观与操作质量。调整入口优先级不能补齐这段能力。

### 2.5 扩展边界存在，自动生成扩展的生产链不存在

当前运行时支持纯规则函数扩展，`rule_effect=false`；SDK 文档明确，未审查的生成代码需要操作系统级隔离，而现有本地进程宿主不能提供该隔离。LLM 编译器尚未形成生成、编译、测试、注册、固定版本并运行扩展的完整链路。

不能把“有 Extension SDK”计为“模型已经可以补齐任何缺失规则”；也不能让生成游戏在 Ursina 内自行维护另一份棋盘，绕过统一状态、回放与 AI 接口。

### 2.6 原先规划有责任需要纠正

选择 IR 的理由是合理的：统一合法性和状态、可回放、可验证、可供 AI 使用，并分离规则与呈现。但我此前把底层模块测试通过、参考包可运行，推断成“只需接入 LLM 即可完成”，这个推断缺少完整转换证据。

旧工单要求短期模型接入、微调，同时冻结已有后端；实际目标却需要编译前端、表达能力、场景后端和验收体系共同开发。必须修正任务范围，不能让工程师仅靠提示工程补齐全部缺口，再让产品设计师逐个报错。

## 3. 标准游戏给出的真正技术要求

已阅读 [标准井字棋](E:/CubeEngine/Dev/3D/tictactoe3d_ursina_v1.py) 与 [纯规则模块](E:/CubeEngine/Dev/3D/tictactoe3d_logic.py)。它不是“二维棋盘复制三层”：

- 连续 3×3×3 棋盘体，27 个格子；可旋转、缩放、悬停、选择外层或内部格子。
- 棋子外观、透明度、碰撞选择与当前可操作层协同工作；已落棋子不能因选层消失。
- 合法落子、交替回合、49 条获胜线、终局反馈、重开、撤销、模式切换。
- 同一套纯规则可供界面与 AI 使用。该文件当前调用 `ai_move_basic`，预留训练模型替换点；不能把这个文件本身说成已经接入训练好的对手。

四个既有三维游戏还提供了其他标准：扫雷的首击安全、邻域计数和展开，2048 的压缩与单次合并，Connect 的重力，Snake 的持续时钟与身体更新。它们都是需要从源项目理解、转换的行为，不能从游戏名字直接套结果。

外观基准已经有可复用做法：`presentation_bridge.py` 从扫雷图集裁剪格子，读取 2048 原配色/字体生成数字表面，复用 Snake 素材；既有 viewer 提供三维相机和交互。这些能力目前有游戏 ID/固定文件名分支。应抽取它们的贴图、字形、相机、选择、动画等通用构件，让编译器从源证据绑定，而非让生成结果调用整套手写游戏类。

## 4. IR 是否可行：结论与边界

做了一个有限但直接的探针：按标准井字棋的 49 条获胜线逐条构造棋盘，分别交给标准逻辑和已有参考 Target IR 判定，**49/49 一致**。

这个探针直接注入状态，证明现有 IR 可表达这项三维胜负能力；它不证明合法操作序列、视觉、AI 或 LLM 转换成功。参考 IR 仍然只是运行时测试材料。

现有 IR 已有多维网格、状态、动作、时钟、事件、随机、邻域/射线/连线等基础。没有证据要求现在推翻这些基础。与此同时，目前只有 `perfect` 信息模型，不能把扫雷的可玩性和不泄漏雷位的 AI 观测支持混为一谈；复杂变长数据操作与资源配方后端也必须逐项实证。

| 方案 | 决策 | 原因 |
|---|---|---|
| 继续一次生成四 IR JSON，增加修补别名 | 停止作为主路线 | 输入不完整，生成负担高，语义验证不足 |
| 模型自由重写整份 Ursina 游戏 | 可作为离线能力对照，不作为产品主架构 | 容易脱离统一状态、回放与 AI 契约，维护和验证困难 |
| 模型编写较高层的游戏程序，工具编译到四 IR，执行测试后修复 | 推荐 | 保留引擎的确定性能力，把模型用于源码理解、算法迁移、空间和视觉设计 |

这里的“较高层”不是先发明一套庞大的第五种 JSON。先做小型、带类型的构建 API：棋盘/状态、动作条件与转移、空间操作、视觉角色、资源配方、输入与 HUD。引用、类型、哈希、Manifest 等机械部分由编译器产生。

能组合现有运算的规则确定性编译到 IR；确实无法表达的算法，通过版本化纯计算能力补齐。模型可以迁移源函数，而不是只能从一个有限游戏名称清单中选择。纯函数只接受显式数据、返回可验证值，状态提交仍由 Rule Runtime 负责。具体函数签名和运行隔离需要在能力验证阶段落实，不能在尚未支持时标成功。

**停止条件：** 如果某个必要规则无法保持正确性地编译，就提交最小反例，增加必要能力或明确缩小支持范围；禁止用另一个手写游戏、常量合法性、假贴图、未执行配方掩盖问题。

## 5. 应在 Workbench 中实现的完整编译流程

```text
导入完整原始项目 + 可选特殊要求
        ↓
可查询的项目证据：源码/依赖/资源/绘制与操作记录
        ↓
生成源游戏程序：状态、规则、交互、视觉角色与生命周期
        ↓
与原游戏对照执行，修复理解错误
        ↓
应用空间变换：规则维度 + 三维输入 + 视觉映射
        ↓
确定性构建 Rule / Scene / Asset / Input + 必要扩展
        ↓
执行玩法、交互和画面检查 → 有界局部修复
        ↓
Workbench 的 Transformed 3D 运行本次转换结果
```

### 源码理解

建立文件、符号、调用关系和资源索引；按任务读取完整相关函数及依赖，不把整个项目塞入一个字符串，也不只给函数名。允许模型调用受限的读取、编译、运行测试、观察画面工具。记录实际读过的代码和出处。

对 Pygame/Turtle 等框架建立通用输入/绘制观察层，获取贴图裁剪、字体、颜色、图形、状态变化和关键帧。完整源码仍然是输入，程序运行记录是补充证据。提取器和测试夹具可以开发，但不得针对一个待转游戏人工重写目标规则再冒充自动转换。

Source 重建是内部正确性门槛，不需要产品设计师手工审批四份文件，也不意味着先完整重写一个独立二维应用才能开始开发三维。先验证与玩法相关的状态、动作和画面绑定。

### 空间变换

区分从源码保留的事实、默认三维设计、用户明确覆盖。增加 Z 不仅修改 extent：还要处理获胜方向、邻域、重力轴、随机生成范围、连续移动和空间输入。

默认策略以现有认可游戏为基准，并按机制应用：有重力的列落子与无重力的自由落子不同，扫雷邻域与 2048 轴向合并不同。复用“连线、邻域、重力、合并”等机制构件是合理的；按 `game == tictactoe` 直接返回完整 Target 不符合自动转换。

来源无法决定且会显著改变玩法的歧义，Workbench 给出简明选择；不要求用户用一段“万能英文”补齐整个游戏。已确认的默认风格和规则无需每次询问。

### 外观恢复：默认执行，与规则并行开发

1. 识别素材和状态的关系：哪张图对应未翻开、旗帜、地雷、棋子、数值；包括图集位置、透明度、字体、颜色与尺寸。
2. 能直接复用的素材直接复用；二维字形/矢量转换成表面、挤出或基础几何；保持图案比例和可读性。
3. Scene 保存格子/实体/界面的视觉绑定和布局；Asset 保存可执行的资源派生。Ursina 后端实际实现这些配方、相机、选择、反馈、动画、HUD 和生命周期。
4. 三维新增状态默认延续原风格。例如扫雷可能有 9–26 个邻雷，原图集只提供 1–8 时，应按原字体和视觉体系构建新增数字，不返回空图、不访问不存在的图块。
5. 自动检查资源来源/裁剪/颜色/字体/绑定；用固定状态和视角截图检查可读性，再用实际点击验证内部格子可选。视觉模型可辅助发现问题，不能替代状态与输入测试。

默认不需要生成式 3D 美术。当前这组棋盘游戏的主要路径是源资源重用与几何重建；不存在“二维素材能唯一确定所有背面”的假设，新增表面遵循引擎默认策略并保持视觉身份。

### 运行与交付

编译期 LLM 做理解和修复；发布的游戏由确定性运行时执行，普通落子不需要再次调用 LLM。图形界面和 AI 从同一权威状态读取，不各自运行一套游戏。

每次转换保存源文件哈希、模型和任务记录、默认策略/意图、测试结果、资源来源、生成产物和版本。失败保留现场；修复能从失败阶段继续，不重做所有成功阶段。模型重试、服务重试、用户改需求分别计数，有预算与取消能力。

Approve 是审阅/信任交付产物的环节，不是获得正确玩法的技术手段。生成文件和 Manifest 是编译器内部工作；常规用户验收不包含复制文件或手动 Attach。

## 6. 统一引擎开发工作包与门槛

按用户最新决策：LLM 是引擎本身的组成部分。源码、Manifest、Inspector 和自然语言是同一转换流程的不同输入方式。以下工作由当前 Codex 在 SRTP 中统一实现编译、运行时、呈现、Workbench 集成和验收，不要求用户再向 AI 工程师派发任务，也不把 llm 分支的新交付作为开始开发的前置条件。后续该分支有独立更新时再正常审查合并。

| 工作包 | 交付与修改范围 | 通过条件 |
|---|---|---|
| W0：修正成功定义 | 列出当前支持能力；取消语义兜底；保留机械规范化。主要在 llm_compiler_v1 | 未知合法性不会变 true；缺规则/资源/交互不能以 schema 通过标为完成 |
| W1：可查询证据与工具循环 | 替换删片段式 evidence；文件/符号读取、完整依赖上下文、运行观察；多阶段任务与局部重试 | 能读到所需完整函数；读取跨文件定义；不依赖 Snake 主题；记录真实来源 |
| W2：构建 API 与表达能力验证 | 高层状态/动作/空间/视觉绑定编译到现有 IR；必要的纯函数扩展接口 | 井字棋空间连线、扫雷展开、2048 合并三个代表性算法能保持语义执行；失败交最小反例和能力缺口 |
| W3：Scene/Asset→Ursina 后端 | 从现有 presentation_bridge/transformed_viewer 抽通用构件，消费编译产物；不得依赖游戏名选择完整逻辑 | 源配色/图集改变后，生成画面跟随改变；X/O、内部选择、状态反馈与主循环可用 |
| W4：Workbench 真正闭环 | 将 W1–W3 接入当前导入与转换工作流；缓存、失败续跑、结果绑定、自动构建包 | 原始二维井字棋输入，界面内生成并玩三维；期间无人手写/替换 Manifest、规则或视图 |
| W5：多游戏与独立变体回归 | 将下表行为和视觉标准纳入 CI/运行验收；使用源码变体、不同意图、未见样例 | 扫雷、2048、Connect、Snake 实际转换；改变源游戏能改变结果，不能靠返回现成模板过关 |
| W6：模型与成本选择 | 相同证据、工具和预算对比可用模型；记录端到端通过率、耗时、费用、人工干预 | 选出工程上可用的默认服务和失败处理；不能只统计 JSON 合法率 |

执行顺序：W0/W1 开始；W2 的规则能力与 W3 的视觉后端同步推进；W4 交付第一个完整路径；W5 的基准从开始就建立，逐个开放正式支持。W6 在工作流有可重复评测后进行。不要先花一轮时间训练模型，再发现模型看不到源码或后端不消费资源。

第一个交付门槛不是“井字棋规则 JSON 成功”，而是用户在同一 Workbench 工作流中得到符合标准的完整井字棋。与此同时，扫雷展开和 2048 合并必须作为能力探针提前进入 W2，防止架构只对井字棋成立。能力探针可人工构造，以检验后端；产品验收不能使用这些人工产物替代自动转换。

不沿用此前依据局部修补估出的剩余小时数/完成百分比。先交 W1–W3 的最小证据和能力缺口，再据真实生成与修复次数估计完整覆盖工期。新的工单要求完整编译工具链开发，工作量超过一次模型接入或一个周末的提示修改。

## 7. 游戏验收矩阵

| 游戏 | 必须保持/转换的行为 | 默认三维体验与特有风险 |
|---|---|---|
| 井字棋 | 轮流、占格拒绝、胜负/平局、终局禁落子、重开；空间 49 线；按标准补齐撤销和对战模式 | 连续棋盘体、可旋转/缩放、内外格选择、X/O、回合和结果；AI 使用同一规则状态。训练权重是独立交付，不捏造已接入 |
| Connect Four | 列落子最低空位、满列拒绝、回合、三维连线、平局 | 重力仍沿指定 Y，Z 扩展列平面；棋子/棋盘外观、落子反馈与空间选择 |
| 扫雷 | 首击安全、布雷数量、26 邻域计数、空域展开、插旗、胜负、重开 | 原图集与数字风格、隐藏状态不能提前显示。AI 的部分可观测接口另立门槛，不能直接复用 perfect 信息声明 |

| Snake | 连续时钟、方向、身体与尾部更新、食物、增长、边界/自撞、计分/重开 | 默认继承原贴图身份，新增 Z 控制与方向呈现；蛇头固定坐标问题继续保留待办 |

测试分层：

- 原始二维源码的状态/事件轨迹，是 Source 行为对照；随机行为用记录的随机结果或明确对应的确定性夹具，不假定两个实现只要 seed 相同就必然相同。
- 适用的机制检查 Z=1 与二维行为一致；有不同二维/三维设计的地方使用显式变换规则对照，不能盲目强求所有策略退化一致。
- 三维目标用独立参考逻辑和性质测试验证，包含合法操作、非法操作、终局与重开；模型生成的测试只是补充，不是唯一裁判。
- 外观在相同状态、固定视角下对照原资源与认可的三维基准；画面、输入、游戏状态联合验收。
- 删除生成缓存，在不同项目路径重跑；重命名文件/符号、更改源配色、棋盘尺寸或合法规则后重跑。给出源哈希→读取证据→生成程序→后端结果记录。不得加载 artifacts 中现成 Target 或游戏专用手写实现完成正式验收。
- 至少保留一个未用于提示示例/修补的源项目或规则变体作独立验收。一次成功只说明该样例成功，不声称任意游戏可转。

## 8. 研究依据与适用范围

本次查阅的一手资料支持的是工程方法，不是 CubeEngine 已具备能力的证明：

- [MLIR Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)：把高层操作分步变成目标真正支持的操作，明确类型与合法性。借鉴分层编译和目标能力约束，不要求把项目迁移到 LLVM/C++，也不把未知操作默认为合法。
- [AlphaCodium](https://arxiv.org/abs/2401.08500)：以执行测试、多阶段生成与修复组织代码生成。这是代码竞赛任务的研究；不能把论文效果数字直接当作游戏还原成功率。
- [OpenGame](https://arxiv.org/abs/2604.18394)：研究复用工具与调试流程的游戏编码代理，把构建与视觉/交互反馈纳入工作流。其主要对象是网页游戏生成，不能据此宣称原始 Python→Ursina 自动迁移已解决。
- [V-GameGym](https://arxiv.org/abs/2509.20136)：说明视觉游戏需要超出代码语法的交互与画面评测。视觉评估不等价于规则等价证明，CubeEngine 仍需独立行为对照。

本地历史依据包括 `SRTP_ENGINE_ARCHITECTURE_V2.md`、`LLM_SOURCE_TO_IR_COMPILER_FRAMEWORK.md`、`SRTP_LLM_ENGINEERING_HANDOFF.md`、`EXTENSION_ADAPTER_SDK.md`，以及历史任务“開發CubeEngine STAL網格生成 (2)”（019fa260-526d-76c0-b2c5-912708c85d1a）。原来关于完整证据、验证和扩展的设计不能继续只停留在文档中。

## 9. 模型、工作方式与用户的职责

服务额度、地区限制和 API 故障属于可用性问题；当前源码证据、语义生成、后端呈现的缺口属于产品实现问题。更换 Gemini 为其他可用模型可能提高可靠性，但不能自动恢复被删的代码，也不能替引擎实现 Scene/Asset 后端。不把继续加 Key 或反复点 Compile 作为开发方案。

先用已可调用的模型建立完整可测链路，再在同样任务上选择模型；暂不把训练或 LoRA 作为前置依赖。需要新调用、费用或数据授权时，按具体实际范围处理，不能用历史小范围许可无限调用。

用户已经明确产品目标、参考质量与主验收游戏，无需再提供技术字段或反复复现错误。用户后续负责验收外观与玩法、决定真正存在歧义的设计取舍；当前 Codex 负责实现并提交可复现的 Workbench 全流程、测试证据与剩余边界。实施状态见 LLM_ENGINE_IMPLEMENTATION_20260922.md；内部能力探针不计作自动转换成功。

本地集成与修改保持 `SRTP`，工程师交付仍用 `llm`，同一个工作目录普通 fetch/merge，不复制工程、不新增逐提交目录。已有手写 Transformed 3D 保留为产品基准和回归参照；本轮不再通过改它的启动优先级解决编译器问题。
