# Spatial Lift 整体体积布局修复

更新说明：本文件下方的验证记录是旧包回归，不是新模型管线验收。后续原生案例审查发现统一覆盖格子外观会丢失素材，已改为按明确呈现角色处理，并把单位间距改为 1.0。完整目标、实际修复和仍未达标的项目见 [原生案例质量审查](REFERENCE_PARITY_REVIEW_20260923.md)。

用户纠正是正确的：横向错开的三个平面没有满足整体 Cube 的转换要求，属于转换失败，不是可推迟的审美微调。上一轮只修复空白与遮挡，没有解决体积语义。

## 本轮改的是引擎

分支 SRTP；本轮模型 API 请求为 0。没有修改当前井字棋 Manifest、Rule/Scene/Asset/Input IR，没有替换游戏规则或导入手写成功样例。

`srtp/volume_layout.py` 定义 `cubeengine.volume-grid/1`，由 Rule 的三维 `rect_grid` 生成一个整体正交体积。当前中心化位置为 `(coordinate - (extent-1)/2) * 1.0`，每格为单位立方体选择区域。多个独立拓扑才分别安排体积；同一拓扑的不同 Z 层不会横向拆开。绑定的动态实体使用同一坐标系统。

该政策通过 `ScenePresentation` 共用于：

- Spatial Lift Scene 执行/行为回放验收；缺失网格投影或少格不能报告成功。
- Spatial Lift Input 的真实宿主事件路由验收。
- Workbench ProjectHost 的 Target 播放，包括已经生成并批准的旧 Target。

Source 视图继续使用原始布局。LLM 契约已明确空间网格布局由引擎拥有；模型仍生成规则、资源和状态外观。当前引擎仅对声明的格壳应用透明容器方法，实体内容保留原几何、贴图和材质；声明的二维背景不进入三维棋盘，明确的三维装饰保留。旧包存在有限兼容分支，不能据此认证新输出质量。所有变换在编译后的呈现层执行，原文件和规则状态保持原样。缓存引擎指纹包含此模块，缓存 Scene 也须重新经过当前验收。

## 修复的连带问题

- 字体提供最小可读尺寸并把生成 HUD 安排到播放器底部。
- 每个格子的线框使用独立 Mesh 实例；共享 Mesh 直接 reparent 会导致只剩最后一个格子有线框。源素材网格也修复了这一实例复用问题。
- 层选择只改变碰撞选取，不移动任何格子。相机旋转、复位沿用同一整体体积。

## 验证

- 实际用户 Target 原包测试：27 格组成 3×3×3，中心 `(1,1,1)` 在世界原点；每格坐标精确符合统一映射。
- 27 格按深度均可被真实 Ursina 射线选中，27 个边框均有独立 Mesh；原规则落子产生可见 X/O，空间对角线判赢、回放、R 重开通过，Manifest 哈希不变。
- 参数化布局回归覆盖 3×3×3、8×8×5、4×4×4、20×20×3；没有任何游戏名条件。覆盖少格/无可视化拒绝、二维不改布局、再次出现剪切时拒绝。
- 全仓 448 项：447 通过、0 失败/错误，1 项付费 API 跳过；四个 Ursina/Panda 渲染探针通过。随后网格实例修复的生成包探针与素材动画/音频探针再次通过。
- 实测图：`.cubeengine_llm/backend_checks/generated_target_playable.png`。原 Manifest 加载后自动落两手，用于验证状态显示；不是手写场景图。

## 保证范围

同类三维矩形网格不会再因为模型输出横向层矩阵而以平面拼图播放；它们共享这一确定性布局。对缺少必要表达的数据仍会报出真实错误，不能承诺下一次模型输出绝无其他 blocker。

不同网格尺寸的布局测试不等于所有游戏的完整转换验收。其他游戏的规则、素材保真、特殊空间结构仍需各自验收；非矩形空间不属于这次政策覆盖范围。

## 用户操作

关闭旧游戏窗口，重新点击 Transformed 3D → PLAY，只能验证已有 Target 的后端回归。完整转换验收必须重新经过 Compile → Spatial Lift，且不得改写生成文件代替引擎修复；现有包能够显示不能证明下一次新转换成功。
