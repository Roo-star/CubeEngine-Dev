# 原生成功案例与 LLM 转换质量：审查及实施记录

2026-09-23；开发分支 SRTP。目标是 Workbench 内从完整二维游戏源码，经模型 Compile、批准、自然语言 Spatial Lift，生成可玩的三维游戏。成功标准对齐用户已有井字棋、扫雷、2048；加载旧包、手改 Manifest、能打开窗口均不能代替新转换验收。

## 结论与技术决策

当前不能声称 B（引擎内转换）已经达到 A（原生手写转换）。主要差距有实际代码证据，并非已证明模型能力不足：

1. A 可以编写任意 Python/Ursina 行为；B 只能使用引擎已实现并向模型准确公布的规则、资源、场景和输入能力。菜单、悔棋、AI 等宿主能力未完整接通时，换更强模型不能自动获得这些能力。
2. 成功案例明确实现了透明格壳、实体内容、原图集映射、状态反馈、深度选择和界面布局。之前通用后端没有完整保留这些区别；上一轮甚至把所有网格根节点的渲染统一覆盖成透明方块，并移除静态渲染，主动损失了源外观。这是引擎处理错误。
3. 当前模型主要读取文本源码和资源证据，尚无完整“执行原游戏、观察状态截图、生成后对照截图”的视觉闭环。外观保真不能仅靠结构校验保证。
4. 过去主要验 IR 能执行和模型自己提供的轨迹。模型自己漏掉的规则/功能可能同时从实现与测试中消失，必须增加独立原游戏基准。

保留 IR：它负责可执行、可验证的游戏定义，不应成为表达能力冻结的边界。采用“通用呈现方法 + 可扩展宿主能力 + 独立行为/视觉验收”；方法同时进入生成契约与执行后端，避免只改 Prompt 或只修输出文件。参考游戏用于提炼方法和作为验收基准，不按游戏名偷偷替换成手写程序。

默认恢复原游戏外观与交互；自然语言用于特殊空间规则或用户明确要求的变化。透明棋盘格壳不应成为扫雷原图块、2048 数字块和其他游戏内容的统一替代品。

## 本轮实际代码变化

- `presentation_patterns.py`：区分 `cell_shell`、`content`、`source_backdrop`、`world_decoration`。透明壳与实体内容分别处理，保留原 mesh、贴图、透明度与比例。旧包仅对无贴图的内置裸方块做有限兼容。
- `component_contracts.py`、`backend_contract.py`、`staged.py`：角色、格心棋子位置、参考方法进入模型可见契约与真实 schema；启动前检查角色枚举一致；引擎指纹更新。
- `volume_layout.py`、`scene_presentation.py`、`ursina_scene_backend.py`：紧凑整体体积、按角色处理背景/装饰、实体棋子居中。没有修改用户生成的 Manifest 来制造本轮结果。
- `quality_assessment.py`、`artifacts.py`、Workbench：生成 `quality.assessment.json`，把“可编译”与“产品质量已验收”分开。未提供独立证据的项目显示 pending，不假定通过。
- `reference_tictactoe_acceptance.py`：49 条线逐步交替落子，与用户原生逻辑逐步核对终局、终局拒绝输入及回放。
- `run_fresh_conversion_acceptance.py`：独立冷启动联调入口。完整 2D 源码 → Source → 自然语言 Lift → 新包规则/渲染检查；禁止阶段缓存，不输入旧 Manifest。记录源码、产物哈希、请求、Intent 和渲染结果。

质量报告目前是已接入的验收框架，不是九类检查均已自动实现。它不会自动宣布 `product_ready=true`。已知角色缺失在报告中标 fail，冷启动联调会停止；普通 Workbench 仍允许查看待验收的编译草稿。尚未建立所有质量不合格自动局部修复/预算管理的闭环。

## 验证结果与边界

本轮 0 次付费 API。离线统一验收禁止网络：454 项，453 通过、0 失败/错误、1 项明确付费 smoke 跳过；4 个实际渲染探针通过。最后的角色契约对齐/冷启动记录调整后，23 项针对性测试再次通过，冷启动入口 `--help` 检查通过。

49 条获胜线检查目前使用已保存的真实模型产物，属于旧包回归；不能证明下一次模型输出正确。冷启动入口尚未执行。它即使完成渲染，也只报告等待独立视觉比较，不宣布达到原生标准。

冷启动联调需单独确定新费用授权：最多 9 次 HTTP、HTTP 自动重试 0、语义修复重试 0，编译/质量失败即停止；请求数不是金额上限。所有输出留在当前 checkout 的正常产物目录，不增加分支或源码副本。
