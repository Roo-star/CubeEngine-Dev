# SRTP Presentation Mapping

SRTP must preserve the source game's presentation identity as evidence, not
invent a replacement art style. Presentation conversion is therefore a
separate, traceable compiler stage after source discovery and before Ursina
rendering.

## Mapping levels

| Source evidence | Deterministic target | Status |
|---|---|---|
| Colours, circles, rectangles, vector primitives | 3D material plus sphere/cube/cylinder primitive | Safe |
| Tile or sprite with a proven state role | Texture repeated on every exposed face of the owning cell/object | Safe |
| Number or glyph generated by source state | One combined surface texture containing both background and glyph | Safe |
| Sprite sheet with proven tile indices | Crop the source atlas, then bind each crop to its state role | Safe |
| Multi-view sprites or explicit normal/depth maps | Billboard, sprite stack, extrusion, or authored mesh | Adapter-dependent |
| One arbitrary front-view bitmap | Back side, depth, topology, rigging and hidden surfaces cannot be recovered uniquely | Function 2/designer handoff |

Ursina entities expose model, texture, material, texture scale/offset and
collider properties, so a proven source tile can be attached to the cell mesh
instead of floating as unrelated UI text. Panda3D additionally supports 2D,
3D and cube-map texture types. These APIs make deterministic surface mapping
possible; they do not make a single 2D image sufficient evidence for a unique
3D object.

References:

- <https://www.ursinaengine.org/api_reference_v8_0_0/entity.html>
- <https://docs.panda3d.org/1.10/python/reference/panda3d.core.Texture>

## World presentation versus UI

World-space assets are lifted with the game state: board tiles, pieces,
characters, food, hazards, state symbols and world materials. Screen-space UI
such as score, timer, menus and pause overlays remains screen-space and is
adapted to the target viewport. Duplicating a HUD along every Z layer would not
preserve the original experience and would create visual clutter.

## Current vertical slices

- Snake: original head/body/tail/apple images are assigned to the corresponding
  3D snake segments and food object. The source presentation is projected onto
  surfaces; it is not claimed to be a newly inferred rigged character model.
- Minesweeper: the original tile atlas is cropped by source state. Covered,
  empty, numbered, flagged and mine states are textures on the cube itself, so
  the symbol rotates with the cell and is visible on exposed faces.
- 2048: the source palette and font setting generate one number-and-colour
  texture per tile value. Detached `Text` entities are not used.
- Connect: source vector circles become red/yellow spheres. The terminal rule
  is independently read from the complete source and lifted across the 13
  straight directions of a cubic lattice.

## Rule Schema evidence

`ui_hints.presentation_mapping` records:

- mapping strategy;
- source asset inventory;
- source-file path for every mapped semantic role;
- unresolved visual roles;
- whether generative 3D or designer input is required.

An adapter must fail visibly when a required role is unresolved. It must not
silently replace source artwork with arbitrary RGB cubes and call that a
faithful conversion.

## Acceptance contract

1. A visual state belongs to the same world entity as its interaction and rule
   state.
2. Rotating the board never leaves numbers or markers floating in screen space.
3. Source and target screenshots can trace each mapped role back to an asset or
   source-authored palette/shape.
4. Input conflicts are explicit: stationary right-click may flag a cell, while
   right-drag remains camera orbit; W/A/S/D remain CubeEngine view controls.
5. Unsupported art inference is labelled unresolved and routed to Function 2
   or a renderer adapter.
